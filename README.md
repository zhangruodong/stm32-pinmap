# stm32-pinmap

审计 STM32 工程的 GPIO 占用：每个物理引脚被哪个模块认领、干什么、多重要。

核心是把**长得像冲突的几种东西分开**：

- ⚠️ **真冲突** —— 同一 target、同一版本内一个引脚被两个模块认领，要改代码
- 🔀 **编译期差异** —— 靠 Keil target 的 `#if defined X` 分家，两个模块从不同时编译进一个 target
- 🧩 **版本差异** —— 同一引脚在 V1.0 / V1.1 板子上用途不同。**编译期不报错**（两套宏同时存在），
  只有运行时的 `if (版本 == …)` 分家。改引脚时只改一套 = 另一版板子静默驱动错外设
- 🔄 **惯用法** —— 同一引脚 in/out 交替（软件 I2C 的标准写法），正常
- ⚪ **没人用** —— 宏定义了但没有活的使用处

**只有第一节要改代码。**

## 装

```bash
git clone <this-repo> ~/.claude/skills/stm32-pinmap
```

或直接把目录拷进 `~/.claude/skills/`。

## 用

```bash
node ~/.claude/skills/stm32-pinmap/scripts/audit.mjs <工程目录>
```

只读，不改任何文件，不调用工具链。输出是 markdown。

工程里有 `.uvprojx` 时自动按每个 Keil target 各扫一遍。只想看某一个：

```bash
node .../audit.mjs <工程目录> --target <target名字>
```

接 Claude Code 之后直接说"这个工程用了哪些 GPIO""引脚有没有冲突"也会触发。

## 报告长什么样

一份 markdown，从整体写到细节。

开头是清单：扫了多少文件、跳过多少行不参与编译的代码、认出几个 Keil target、
识别到几个引脚、有哪些运行期版本标签。

接着是引脚占用表，一行一个"谁在认领这个引脚"：

| 引脚 | 重要度 | 功能 | 方向 | 版本 | 写法 | target | 定义处 |
|---|---|---|---|---|---|---|---|
| **PB13** | 🔴 会动/停不下来 | AIN1 | out | — | 位带 | CarA, CarB | `Inc/motor.h:2` |
| **PA09** | 🟠 失控/通信断 | UART1_TX | ? | — | 端口对 | CarA, CarB | `Inc/bus.h:12` |
| **PD14** | 🔵 只是不方便 | LED_R | out | V1_0 | 位带 | CarA, CarB | `Inc/led.h:8` |

「方向」是 `?` 表示端口对宏只说了引脚、没说是读还是写。
同一个引脚被几个名字认领就是几行，第一列只在头一行写引脚号。

再往下是五节分类，就是开头那张表里的五种东西，一种一节。

最后两块是改引脚时对着看的：

- **时钟未使能** —— 有引脚定义，但全工程没找到那句 `RCC_AHB1PeriphClockCmd(...)`。
  可能时钟在别处打开，也可能真漏了
- **运行时分发点** —— 所有「版本变量 `== …`」的位置。改引脚时这几行必须同步看

## 认哪些写法

| 写法 | 例子 |
|---|---|
| 位带宏 | `#define AIN1 PBout(13)` |
| 端口对 | `#define PWMA_PORT GPIOC` + `#define PWMA_PIN GPIO_Pin_9` |
| 标准库 | `GPIO_InitStruct.GPIO_Pin = ...; GPIO_Init(GPIOB, &...)` |

`_TIM` 和 `_Channel` 会顺带带出来，表格里写成 `端口对 + TIM4_CH2`。
端口对是按宏名配对的，同名候选超过一个就取同文件、40 行内的那个。

工程里有 `.uvprojx` 就还会读每个 target 的 `<TargetName>` 和 `<Define>`。

## 怎么判断

规则不多，但每条都挨过坑，源码注释里都写着。

1. **先判死条件编译。** `#if 0` / `#if 1` / `#if defined X` / `#else` / `#elif` 都解得出来；
   解不出来的（`#if VERSION > 2`）**两个分支都留**——宁可多报，也不能漏掉真在用的引脚。
2. **每个 Keil target 各扫一遍**，用 `<Define>` 解 `#if defined X`。
3. **归属到 target 看调用点，不看定义处。** 引脚定义通常是无条件的，
   真正决定谁活的是 `#if defined CAR_A` 里那行 `Servo_Init()`。所以得走一遍调用图。
4. **调用图**从 `main`、`*_Handler`、`*_Task` 这些根往下走。FreeRTOS 是把函数名当参数
   `xTaskCreate(Task, ...)` 传进去的，抓不到调用边，所以任务函数也当根。
5. **同一个文件里、同一个引脚上的多个名字合成一行。** 一个文件就是一个模块，
   模块不会跟自己抢引脚。
6. **分类顺序**：编译期差异 → 惯用法 → 同文件合并 → 版本差异 → 真冲突。
   只有真冲突要求两边都真的有人用——另一边压根没人用的话，那是第五节的事。

## 调

```bash
cp scripts/pinmap.config.example.json pinmap.config.json
node .../audit.mjs <工程目录> --config pinmap.config.json
```

可用的旋钮：

| | |
|---|---|
| `skip` | 跳过的目录名 |
| `levels` | 引脚重要程度的分档正则，按自己的项目改 |
| `defaultLevel` | 一个都没匹配上时的档位 |
| `roots` | 程序入口函数名，调用图的起点 |
| `ignore` | 当成不算冲突的宏名 |
| `versionVar` | 判定"运行在哪版硬件上"的变量名。默认认 `Hardware_Ver` / `HW_Ver` / `BoardVer` / `PCBRev` 这类，对不上就填自己的 |

**把 `pinmap.config.json` 加进 `.gitignore`** —— 里面是你的项目事实，不该跟代码一起走。

## 自检

```bash
node scripts/selftest.mjs
```

造假工程跑一遍，断言五类分类没有互相串。回归基本都栽在正则上，
所以这里锁的是「位带宏没漏开头那个 `P`」「`#if 0` 死分支跳过」「车型宏按 target 分开」
这类会**静默返回错结果**的地方。

出问题时：

```bash
node scripts/audit.mjs <工程目录> --debug
```

把调用图统计打到 stderr（不进报告）——查「这个引脚为什么被判成没人用」先看它。

## 边界

- **不算真正的预处理器。** 字面 `#if 0` / `#if 1` 判死；有 `.uvprojx` 时 `#if defined X` 也能判；
  其余（`#if VERSION > 2`、依赖 `#include` 链的宏）求不出来，两个分支都保留
- 「有没有人用」是照 `*_Init()` 调用图推的，不是真静态分析；推不出来会在报告头打 ⚠️ 并关掉这个判断
- `#include` 不跟，跨文件 include 进来的引脚定义看不到
- 时钟只认 `RCC_AHB1PeriphClockCmd`，APB1/APB2 或直接写寄存器会报成"未使能"（报告里已注明）
- `GPIO_Init()` 风格靠前 12 行内的 `GPIO_Pin =` 关联端口

三个踩过的坑，都在源码注释里：

1. **`#if 0` 的备用接法照样是活文本。** 板级头文件里注释掉的那几套接法不判死就会全算在用，
   凭空造一堆冲突。判定前还得先剥掉行尾注释——`#if 0 //PA11` 直接比字符串会判成"条件未知"。
2. **`#if` 栈必须用剥过注释的行来推。** 被 `/* */` 注释掉的 `#if` / `#endif` 会让栈错位，
   后面的 `#if defined X` 整个失效。
3. **CRLF 会让函数检测整个哑掉。** 以 `$` 结尾的正则碰到行尾 `\r` 静默失效，
   那个文件的使用处全掉进"文件级"、无条件算活——结果是**冲突全部消失**，报告干净得可疑。
   这种错比假阳性危险，因为看不出来。
